03 // SOFTWARE DEVELOPMENT LIFECYCLE (SDLC)

Khaotic Labs uses a custom Agile Sprint Machine methodology — a lean, deterministic SDLC designed for solo execution at maximum velocity. The process is sequential, approval-gated, and leaves no ambiguity.

3.1  Phase 1 — Agile Discovery & Stack Selection

Triggered by: Any new project engagement

Deliverables: A single comprehensive Markdown document containing:

Core Mechanical Problem: The fundamental engineering challenge in JPE.

The Moat: The product's technical or strategic competitive advantage.

Stack Selection: Optimal languages, frameworks, and interfaces with justification.

File-Tree Blueprint: Complete directory architecture.

Sprint Backlog: Prioritized list of modular Sprint Tasks (Step 1, Step 2, Step 3...).

Gate: Zero execution begins without explicit client/founder approval.

3.2  Phase 1 (Alt) — Codebase Ingestion (Existing Projects)

Triggered by: Adding features or refactoring to an existing codebase

Deliverables:

Stack & Architecture Identification: Languages, frameworks, structural patterns detected.

Technical Debt & Threat Audit: Syntax bugs, performance bottlenecks, security vulnerabilities.

Targeted Sprint Backlog: Incremental roadmap for the new feature within existing constraints.

3.3  Phase 2 — Sprint Execution

Execution cycle per sprint task:

Step-Back Reasoning: Before any code, map abstraction, logic flow, and safety/threat surface.

Code Delivery: Complete, un-truncated file or function. No placeholders. No "// rest of code here."

Micro-Demo Checklist: Short JPE checklist for local validation before advancing.

Gate: Wait for explicit approval or validation before moving to the next task.

3.4  Phase 3 — Surgical Diagnostics

Triggered by: Compiler error, runtime panic, or unexpected behavior at any phase

Hypothesis: Identify exact line, type mismatch, or logic error.

Context Cross-Reference: Check for RAG context collapse or historical hallucination.

JPE Root Cause Analysis: Plain English explanation of what broke and why.

Surgical Fix: Only the corrected function. Zero orphaned variables or broken comments.

Log Entry: Bug pattern gets flagged to .corrections.log and evaluated for pkg/ extraction.

3.5  Phase 4 — Production Deploy

Standard deployment pipeline:

  Code → GitHub (private) → Cloudflare Pages → Live URL

SPA routing fix: _redirects file in public/ with rule:

  /* /index.html 200

Database: Turso — one database per client (100 free databases, 5GB storage).

Automation: n8n self-hosted via Docker + Cloudflare Tunnel for zero-cost workflows.

05 // OPERATIONAL RULES & STANDARDS

5.1  Scope Neutrality

All project contexts are isolated by default. A resource or library is only shared between projects if it is explicitly located in the shared pkg/ or .khaotic/ base directories. Cross-contaminating client contexts is a critical failure.

5.2  Recursive Feedback & .corrections.log

When a recurring bug or sub-optimal process pattern is identified, it must:

Be logged to .khaotic/.corrections.log with a clear description and root cause.

Be evaluated as a candidate for extraction into a pkg/ shared library or protocol.

Inform the sprint process to prevent the same error class from occurring again.

5.3  Zero-Capital Focus

Every architectural decision is evaluated against the question: "Can this be achieved at zero or near-zero cost without sacrificing quality?" The answer must be yes before any paid service is considered. The current operational cost of Khaotic Labs at full capability is the cost of two existing subscriptions (Claude Pro + Google AI Pro) — everything else is free.

5.4  Data Integrity

User-provided images, photos, and raw data assets are never modified, augmented, cosmetically altered, or processed without explicit instruction. This is a hard constraint, not a preference.

5.5  Security Standards

All client data is isolated in dedicated Turso databases. No cross-client data access is ever permitted. All AI model usage routes through secure API endpoints (Claude Pro and Google developer tiers) where data is encrypted in transit, isolated per-request, and explicitly not used to train public LLM models. This guarantee must be documented in all client contracts.
